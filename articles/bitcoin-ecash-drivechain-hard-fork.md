## はじめに

2026年8月、国内の暗号資産取引所が「Bitcoin（BTC）のハードフォーク」を理由に、BTCの入出金を一時停止すると発表しました。

このハードフォークによって作られる新しいチェーンが、**eCash（ECX）**です。

「Bitcoin自体が新しい仕様へ移行するのか」「持っているBTCがECXに変わるのか」と思うかもしれません。しかし今回の計画は、Bitcoinネットワーク全体が新ルールへ移行するアップグレードではありません。

一言でまとめると、次のような試みです。

> Bitcoinで採用されなかったDrivechainを実験するため、Bitcoinの履歴から新しいチェーンを立ち上げる試み

この記事では、eCashがBitcoinからどのように分岐するのか、Drivechainを構成するBIP 300とBIP 301とは何か、なぜ取引所がBTCの入出金を停止したのかを整理します。

:::message
この記事で扱うeCashのティッカーは`ECX`です。Bitcoin Cashから分岐した既存のeCash（`XEC`）とは別の暗号資産です。
:::

## 先に結論

eCash（ECX）の要点は次のとおりです。

- Bitcoinのブロック履歴とUTXOセットを引き継いで、別のネットワークとして分岐します
- BTC本流のコンセンサスルールは変わらず、BTCの残高も移動しません
- フォーク時点のBTC残高に対して、ECXチェーン上で原則1対1のECXが作られます
- BitcoinではDraftのまま採用されていないBIP 300とBIP 301を有効化します
- BIP 300は、基軸チェーンとサイドチェーンの間で資産を移動するHashrate Escrowを定義します
- BIP 301は、マイナーがサイドチェーンを直接検証せずに関与できるBlind Merged Miningを定義します
- BTCとECXは同じ鍵・アドレス形式を使うため、分岐前のUTXOを動かす際にリプレイリスクがあります
- ECXの取得や取り扱いは、秘密鍵を自分で管理しているか、取引所に預けているかで異なります

したがって、今回のハードフォークを「BitcoinにDrivechainが実装された」と表現するのは正確ではありません。Drivechainが実装されるのは、Bitcoinから分岐したECXチェーンです。

## eCash（ECX）とは何か

eCashは、LayerTwo LabsのPaul Sztorc氏らが進めるBitcoinのハードフォークです。Paul Sztorc氏は、Drivechainを定義するBIP 300とBIP 301の著者でもあります。

新しいブロックチェーンをゼロから開始するのではなく、あるブロック高までのBitcoinの履歴を引き継ぎます。分岐地点まではBTCとECXが同じ履歴を持ち、そこから先はそれぞれ独立したルールでブロックを追加します。

```text
                         ┌─ Bitcoinチェーン
Bitcoin共通履歴 ─ 分岐点 ┤  従来のルールで継続
                         │
                         └─ eCashチェーン
                            Drivechainを有効化して継続
```

分岐後は、次のものが別々になります。

- P2Pネットワーク
- ブロックとトランザクション履歴
- コンセンサスルール
- ハッシュレートとチェーンの安全性
- BTCとECXの市場価値

BTCを1枚持っていたからといって、価値が自動的に2倍になるわけではありません。ECXの価格はECX側の需要、流動性、取引所対応、ハッシュレートなどによって別に決まります。

### 「Bitcoinのアップグレード」ではない

ハードフォークには、既存ネットワークの参加者が合意して新ルールへ移行するアップグレードと、旧ルール側を残したまま別の暗号資産として分岐するケースがあります。

今回のeCashは後者です。Bitcoin CoreやBTC利用者がECXソフトウェアへ更新しなければならないわけではなく、BTCチェーンは従来どおり動き続けます。

この意味では、2017年にBitcoinからBitcoin Cashが分岐した構図に近いものです。ただし、分岐の目的や新しく導入する機能は異なります。

## なぜeCashを作るのか

eCashの中心的な目的は、**Drivechain**を実際のネットワークで稼働させることです。

Drivechainは、Bitcoinのような基軸チェーンに複数のサイドチェーンを接続する構想です。サイドチェーンごとに異なるルールを採用できるため、基軸チェーンを複雑にせずに新しい機能を試せます。

例えば、サイドチェーン側では次のような設計を選択できます。

- 大容量ブロックを使った決済
- 強いプライバシー機能
- EVMなどのスマートコントラクト環境
- 予測市場
- 名前・IDシステム
- Bitcoin Scriptとは異なる実行環境

利用者は、必要なサイドチェーンだけを選びます。すべての基軸チェーン利用者が、すべてのサイドチェーンを検証する必要はありません。

BIP 300とBIP 301は、もともとBTC上でDrivechainを動かす提案としてBitcoinのBIPリポジトリに公開されました。しかし、2026年9月7日時点ではどちらも`Draft`で、BTCのコンセンサスルールには採用されていません。

そこでeCashは、BTCへの採用を待つのではなく、Bitcoinの履歴から別チェーンを作り、そのチェーンでBIP 300とBIP 301を有効化します。

## BIP 300：Hashrate Escrow

BIP 300は、基軸チェーンとサイドチェーンの間でコインを移動する**two-way peg**を定義します。仕様上の名称は**Hashrate Escrows**です。

通常のsidechain federationでは、複数の署名者がpegにロックされた資金を共同管理します。BIP 300は固定された署名者の代わりに、Proof of Workを作るマイナーの長期間の投票によって、サイドチェーンからの出金を承認します。

### BIP 300が管理する二つの状態

BIP 300対応ノードは、主に次の二つのリストを追跡します。

| 状態 | 内容 |
| --- | --- |
| D1: Sidechain List | 提案・有効化されたサイドチェーンと、その資金を保持するUTXOを記録する |
| D2: Withdrawal List | サイドチェーンから提出された出金bundle、work score、残り投票期間を記録する |

D1には各サイドチェーンの番号、名前、バージョン、ソフトウェアを示すhash、稼働状態などが入ります。さらに重要なのが**CTIP（Critical Transaction Index Pair）**です。

CTIPは、そのサイドチェーンに預けられたコイン全体を保持する、現在のEscrow UTXOを`txid`と`vout`の組で指します。

```text
D1: Sidechain List

Sidechain #3
  name    = Example Chain
  active  = true
  CTIP    = txid:vout  ──→ 現在のEscrow UTXO
```

サイドチェーンごとに利用者別のL1 UTXOを大量に作るのではなく、入出金のたびに古いCTIPを使用し、新しい残高を持つCTIPへ更新します。この構造により、pegへ入った資金の合計と現在位置を基軸チェーン側で追跡できます。

### 6種類のメッセージ

BIP 300は、サイドチェーンの登録、出金投票、実際の入出金を6種類のメッセージに分けています。

| メッセージ | 役割 |
| --- | --- |
| M1: Propose New Sidechain | 新しいサイドチェーンと使用するslotを提案する |
| M2: ACK Proposal | マイナーがサイドチェーン提案を支持する |
| M3: Propose Bundle | サイドチェーンからの出金bundleをD2へ登録する |
| M4: ACK Bundle | マイナーが各サイドチェーンの出金候補へ投票する |
| M5: Deposit | 基軸チェーンからサイドチェーンへ資金を追加する |
| M6: Withdrawal | 承認済みbundleを実行し、基軸チェーン側へ払い出す |

M1からM4は、主にcoinbase transactionの`OP_RETURN`へcommitmentを記録します。M5とM6はEscrow UTXOであるCTIPを実際に更新するトランザクションです。

### M1とM2：サイドチェーンを登録する

新しいサイドチェーンは、空いているsidechain slotを指定してM1で提案されます。M1には名前や説明のほか、sidechain softwareのtarballやGit commitを示すためのhashが含まれます。

ただし、このhashが指すプログラムを基軸チェーンのノードが実行・検証するわけではありません。どのソフトウェアを使うべきかを人間が確認するための情報です。

提案後、マイナーはM2でその提案をACKします。空きslotに対する提案では、次の2,016ブロックのうち1,008回以上failが付くと有効化に失敗します。言い換えると、提案の登録にもハッシュレートによる継続的な支持が必要です。

```text
M1: Sidechain #3を提案
  ↓
マイナーが各ブロックのM2でACK
  ↓
必要な支持を維持
  ↓
D1でSidechain #3をActiveにする
```

### M5：サイドチェーンへ入金する

サイドチェーンへのdepositでは、現在のCTIPを使用し、入金額を加えた新しいCTIPを作ります。

```text
現在のCTIP: 100 ECX
利用者の入金: 5 ECX
        ↓
新しいCTIP: 105 ECX
```

基軸チェーン側で確認できるのは、Escrowに入ったコインが100 ECXから105 ECXへ増えたことです。どのサイドチェーン利用者へ5 ECX分をcreditするかは、サイドチェーン側がdeposit transactionを検証して判断します。

通常の送金のように同じコインがチェーン間を直接移動するわけではありません。基軸チェーンでロックされた量に対応する残高をサイドチェーンで認識し、二重に利用できないようにします。

### M3とM4：出金bundleへ投票する

難しいのは、サイドチェーンから基軸チェーンへ戻る方向です。

基軸チェーンのフルノードは、サイドチェーンのトランザクションやコンセンサスルールを検証していません。そのため「Aliceがサイドチェーンで3 ECXをburnしたので、基軸チェーンで3 ECXを返してよい」と直接判断できません。

BIP 300では、サイドチェーン上の複数の出金要求を一つの**withdrawal bundle**へまとめます。bundleは、最終的にL1上で複数の利用者へ支払うトランザクションの候補です。

```text
サイドチェーン上の出金要求
  Alice: 3 ECX
  Bob:   2 ECX
  Carol: 1 ECX
       ↓ まとめる
Withdrawal bundle: 合計6 ECX
```

M3は、bundleそのものではなく、出金トランザクションから計算した**blinded hash**をD2へ登録します。実際の入出力の一部を後でCTIPや手数料に合わせられるようにしつつ、支払先と金額にはcommitする構造です。

登録されたbundleには、次の二つの値が付きます。

- `ACKs`：マイナー投票を表すwork score
- `Blocks Remaining`：投票できる残りブロック数

M4は、各sidechain slotについてどのbundleを支持するかをupvote vectorで示します。work scoreは1ブロックにつき最大1だけ増減し、`Blocks Remaining`は毎ブロック1ずつ減ります。

仕様上、bundleは26,300ブロックの期間内にwork score 13,150へ到達すると成功します。約10分のブロック間隔で単純換算すると、投票期間は最大約6か月です。

```text
M3でbundle hashを登録
  ACKs = 1
  Blocks Remaining = 26,299
       ↓
各ブロックでM4による投票
       ↓
ACKs >= 13,150
       ↓
M6を実行可能
```

期間切れになったbundleや、残り全ブロックで支持されても13,150へ届かなくなったbundleはD2から削除されます。複数候補を無制限に並行処理するのではなく、最終的に承認された一つのbundleが全出金をまとめて実行します。

### M6：承認されたbundleを払い出す

work scoreが閾値へ到達すると、そのblinded hashに対応するM6 withdrawal transactionを基軸チェーンへ含められます。

M6は現在のCTIPを使用し、次の二つを同時に行います。

1. bundleに含まれる利用者へ出金する
2. 出金されなかった残高を新しいCTIPへ戻す

```text
現在のCTIP: 105 ECX
承認済み出金: 6 ECX
        ↓
利用者へ:      6 ECX
新しいCTIP:   99 ECX
```

これにより、Escrowの資金を保持するUTXOは常に新しいCTIPへ移ります。BIP 300対応ノードは、M6のblinded hashが承認済みであること、先頭outputが新しいCTIPであること、手数料や追加の`OP_DRIVECHAIN` outputが仕様を満たすことを検証します。

### BIP 300のセキュリティモデル

長い投票期間を設けるのは、不正なbundleが提案された場合に利用者が検知し、マイナーや市場へ警告する時間を確保するためです。

しかし、基軸チェーンのノードはサイドチェーンの正当性を検証しません。確認できるのは「マイナーがこのbundle hashを長期間ACKした」という事実です。

そのため、資金の出口をマイナーの投票に依存する点は変わりません。

- マイナーが正当な出金を検閲する可能性
- マイナーが結託して不正な出金bundleを承認する可能性
- 出金確定まで数か月かかり得ること
- ハッシュレートが少数の事業者へ集中した場合の安全性

DrivechainはFederationが鍵を管理する方式とは異なりますが、信頼を完全になくすわけではありません。信頼と攻撃の対象を、固定された署名者からマイナーの継続的な投票へ移す設計だと捉えられます。

## BIP 301：Blind Merged Mining

BIP 301は、**Blind Merged Mining（BMM）**を定義します。

BIP 300がサイドチェーンの登録と資金移動を扱うのに対し、BIP 301が扱うのは、**誰のサイドチェーンブロックを次のブロックとして採用するか**です。

通常のマージドマイニングでは、マイナーが補助チェーンのノードも動かし、そのチェーンのブロックを構築・検証します。チェーンが増えるほど、マイナーが運用するソフトウェアと障害リスクも増えてしまいます。また、補助チェーンの報酬はそのチェーン固有の通貨で支払われるのが一般的です。

BMMでは、サイドチェーンの利用者がブロック候補を作り、基軸チェーンのマイナーから「このブロックhashをcommitしてもらう権利」を入札で買います。

BMMでは、役割を次のように分けます。

```text
サイドチェーン利用者
  ├─ サイドチェーンのトランザクションを検証
  ├─ 次のブロック候補を作る
  └─ そのブロックを採用してもらうため入札する

基軸チェーンのマイナー
  ├─ 入札を選ぶ
  ├─ 選んだサイドチェーンブロックのハッシュを記録
  └─ 入札額を手数料として受け取る
```

マイナーはサイドチェーンの全状態を確認せず、選択したブロックハッシュへのコミットメントを基軸チェーンのcoinbase transactionへ含めます。マイナーから見るとサイドチェーンの中身を確認しないため、Blind Merged Miningと呼ばれます。

これにより、マイナーはサイドチェーン専用ノードを運用せず、サイドチェーンから収益を得られます。サイドチェーン側は、独自のProof of Workを一から構築する代わりに、基軸チェーンのブロック生成と結び付けられます。

ただし、マイナーがサイドチェーンを検証してくれるわけではありません。サイドチェーン利用者は、自分が使うチェーンのノードを動かし、サイドチェーンのルールを自分で検証する必要があります。

### BMM Request：ブロック候補への入札

次のサイドチェーンブロックを作りたい利用者を、BIP 301の説明に合わせてSimonとします。

Simonはサイドチェーンノードを動かし、有効なトランザクションを選んでブロック候補を作ります。そのブロックhashを`h*`とします。

次にSimonは、`h*`を基軸チェーンへcommitしてもらうための**BMM Request**を作ります。Requestには主に次の情報が含まれます。

- 対象のsidechain番号
- 採用してほしいサイドチェーンブロックhash `h*`
- 一つ前の基軸チェーンblock hash
- 基軸チェーントランザクションの手数料としてマイナーへ支払う入札額

一つ前の基軸チェーンblock hashを含めるため、Requestは特定の次ブロックにだけ有効です。基軸チェーンで新しいブロックが見つかれば、採用されなかったSimonは新しいtipを参照して入札を作り直します。

```text
Simon A: sidechain block hash = hA、入札 = 1,000 sat
Simon B: sidechain block hash = hB、入札 = 3,000 sat
Simon C: sidechain block hash = hC、入札 = 2,000 sat
```

同じsidechainについて複数のSimonが異なるブロック候補を提示できます。マイナーは、その中から一つを選びます。

### BMM Accept：マイナーが一つの候補を選ぶ

基軸チェーンのマイナーをMaryとします。

Maryは選んだ`h*`を、基軸チェーンのcoinbase transactionにある`OP_RETURN` outputへ**BMM Accept**として記録します。

```text
BMM Accept
  OP_RETURN
  message header
  sidechain number
  selected sidechain block hash h*
```

同じsidechainについて、1回の基軸チェーンブロックで受理できる候補は一つです。Maryが`hB`を選ぶと、`hB`を提示したSimon BのRequestだけが条件を満たし、Maryはその入札手数料を受け取れます。

```text
MaryがhBをcoinbaseへcommit
       ↓
Simon BのBMM Requestだけが成立
       ↓
Maryは3,000 satを受け取る
       ↓
サイドチェーンではhBが次ブロックになる
```

マイナーが入札手数料を受け取るには、対応する`h*`をcoinbaseへcommitしなければなりません。この条件によって、入札の支払いとサイドチェーンブロックの選択を基軸チェーン上で結び付けます。

### サイドチェーン手数料がマイナーへ届く流れ

Simonが作ったサイドチェーンブロックに、合計10,000 sat相当の手数料が含まれるとします。

Simonはそのうち9,500 satをBMM RequestでMaryへ入札できます。落札できれば、Simonはサイドチェーン側で10,000 sat相当を受け取り、基軸チェーン側で9,500 satを支払います。差額の500 sat相当がSimonの利益になります。

```text
サイドチェーン手数料収入: 10,000 sat相当
基軸チェーンへの入札:      9,500 sat
                               ────────
Simonの差額:                  500 sat相当
Maryの収入:                 9,500 sat
```

競争相手が増えれば、Simon同士がより高い入札を提示し、サイドチェーン手数料の多くが基軸チェーンのマイナーへ流れることが期待されます。

### 「Blind」は検証不要という意味ではない

Maryは`h*`を選びますが、そのサイドチェーンブロックの全トランザクションを検証する必要はありません。ここがBMMの運用上の特徴です。

しかし、サイドチェーンの利用者までblindでよいわけではありません。サイドチェーンノードは`h*`に対応するブロックを取得し、次を自分で検証します。

- 親ブロックへ正しく接続しているか
- サイドチェーンのconsensus ruleを満たすか
- 二重支払いがないか
- coinbaseと手数料配分が正しいか
- 基軸チェーンに正しいBMM Acceptが存在するか

Maryが無効なサイドチェーンブロックへcommitしても、検証するサイドチェーンノードはそのブロックを拒否できます。ただし、その基軸チェーンブロックに対応する期間について、サイドチェーンが有効なブロックを生成できない、または一時的に進まなくなる可能性があります。

### 従来のmerged miningとの違い

|  | 従来のmerged mining | Blind Merged Mining |
| --- | --- | --- |
| 補助チェーンblockの作成 | 通常はマイナー側 | サイドチェーン利用者側 |
| 補助チェーンnode | マイナーも運用する | マイナーは運用しなくてよい |
| マイナーの報酬 | 補助チェーンの通貨 | 基軸チェーン上の入札手数料 |
| 採用候補 | マイナーが直接構築 | 入札された`h*`から一つ選ぶ |
| 補助チェーンの検証 | マイナーも関与 | サイドチェーン利用者が担当 |

### BIP 300とBIP 301を組み合わせる

BIP 300とBIP 301は役割が異なります。

```text
BIP 300
  ├─ どのサイドチェーンを有効にするか
  ├─ ECXをどうロックするか
  └─ ECXをどう引き出すか

BIP 301
  ├─ 次のサイドチェーンblock候補を誰が作るか
  ├─ マイナーがどの候補へcommitするか
  └─ サイドチェーン手数料をどうマイナーへ渡すか
```

利用者がECXをサイドチェーンへdepositし、そのチェーン上で取引し、最後にECXへ戻すまでの全体像は次のようになります。

```text
1. M1/M2でサイドチェーンを登録
        ↓
2. M5でECXをEscrowへdeposit
        ↓
3. BIP 301のBMMでサイドチェーンblockを生成
        ↓
4. サイドチェーン上で取引
        ↓
5. 出金要求をbundleへまとめる
        ↓
6. M3/M4でbundleを長期間投票
        ↓
7. M6で承認済みbundleをECX側へ払い出す
```

この構成では、BIP 301がサイドチェーンを日々進め、BIP 300が基軸チェーンとの資金の境界を管理します。

:::message
BIP 300/301は本来BTCへのソフトフォーク案として書かれています。そのため仕様書では基軸資産をBTCと表記しています。eCashでは同じ仕組みをECXチェーンで有効化するため、実際にEscrowへ入る基軸資産はECXです。BTC本流のコインがECXのDrivechainへ直接移動するわけではありません。
:::

## DrivechainとLightning Networkの違い

DrivechainとLightning Networkは、どちらも基軸チェーンの外で処理を増やす構想ですが、仕組みと目的が異なります。

|  | Lightning Network | Drivechain |
| --- | --- | --- |
| 主な用途 | 高速・少額決済 | 独自ルールを持つサイドチェーン |
| 基本単位 | ペイメントチャネル | 独立したブロックチェーン |
| 状態更新 | 参加者間の署名 | サイドチェーンのブロック |
| L1との接続 | funding・commitment transaction | Hashrate Escrow |
| 主な安全性 | 鍵、HTLC、タイムロック、監視 | サイドチェーン検証とマイナー投票 |
| 機能の自由度 | 支払い中心 | チェーンごとに変更可能 |

LightningはBitcoinのコンセンサスルールを変更せず、チャネル参加者間で未公開トランザクションを更新します。Drivechainは、独自のコンセンサスルールとブロックを持つ別チェーンを接続します。

両者は必ずしも排他的ではありません。サイドチェーン上にLightning型のチャネルを構築したり、Lightningを使って異なるチェーン間の支払いを中継したりする設計も考えられます。

## フォーク時にBTCとECXはどうなるのか

eCashはフォーク地点のBitcoinのUTXOセットを引き継ぎます。そのため、フォーク前から存在するBTCの秘密鍵は、ECXチェーン上に複製された対応UTXOも制御できます。

```text
フォーク時点で秘密鍵Kが制御する1 BTC

Bitcoinチェーン: 秘密鍵Kで1 BTCを使用できる
eCashチェーン:   秘密鍵Kで原則1 ECXを使用できる
```

BTC側のコインが移動したり、Bitcoinネットワークから引き出されたりするわけではありません。二つのチェーン上に、同じ鍵で制御できる別々のUTXOが存在する状態になります。

### セルフカストディと取引所保管の違い

秘密鍵を自分で管理している場合、ECX側の対応UTXOも原則として自分で制御できます。

取引所にBTCを預けている場合、オンチェーンの秘密鍵とフォーク時点のUTXOを管理しているのは取引所です。利用者にECXを付与するか、売却して金銭で還元するか、そもそも対応しないかは各取引所の方針によります。

「フォーク時点でBTCを保有していれば、必ず誰でもECXを受け取れる」とは限りません。取引所口座のBTC残高は、利用者自身が管理するオンチェーンUTXOではないためです。

## なぜリプレイ攻撃が問題になるのか

BTCとECXは分岐前の履歴だけでなく、鍵やアドレスの形式も共有します。公開されているECXの統合資料では、P2PKH、P2SH、SegWit、Taprootのアドレス形式や、秘密鍵・拡張鍵の形式がBitcoinと同じです。

このため、分岐前のUTXOを使うトランザクションが両方のチェーンで有効になる場合があります。

```text
ECXを送るトランザクションを作成
       │
       ├─ ECXチェーンで承認
       │
       └─ 同じトランザクションをBTC側へ再送
          → 条件が同じならBTC側でも承認される可能性
```

一方のチェーンで公開されたトランザクションを、別のチェーンで再利用する行為がリプレイです。ECXだけを送るつもりだったのに、対応するBTCまで送られてしまう危険があります。

ECXの公開資料では、`nLockTime = 499999999`を設定したECXトランザクションをBitcoin側で恒久的に無効とする、オプトイン方式のリプレイプロテクションが説明されています。

ただし、すべてのウォレットや利用者が必ずこの方式を使うとは限りません。また、分岐直後はウォレット、取引所、カストディ事業者の実装が十分に検証されていない可能性があります。

これが、bitbankなどの取引所がBTCの入出金を一時停止した主な理由です。Bitcoinチェーンが停止するからではなく、顧客資産を安全に分離し、意図しないリプレイや入金の誤認識を防ぐための措置です。

:::message alert
ECXを取得するため、現在BTCを保管しているウォレットのシードフレーズや秘密鍵を、未検証のECXウォレットへ入力するのは危険です。ECX側のソフトウェアに秘密鍵を渡す前にBTCを新しい鍵へ移す方法もありますが、実際に操作する場合は正式仕様と検証済み手順を確認する必要があります。
:::

## Satoshi時代のコインを再割り当てする議論

eCashには、Drivechainとは別に大きな論点があります。Satoshi Nakamotoが採掘したと推定される古いコインの一部を、ECXチェーン上で別の宛先へ再割り当てする計画です。

2026年9月7日時点で公開されているdrynet4の資料では、220件のトランザクションを`repurpose`対象としてホワイトリスト化し、通常の署名なしでコインを再割り当てする仕組みが記載されています。

これはBitcoinチェーン上のBTCを動かすものではありません。ECXチェーン上へ複製されたコインだけが対象です。しかし、ECXのコンセンサスルールが秘密鍵による所有権へ例外を設けることになるため、次のような批判があります。

- 秘密鍵を持たない開発者がコインの所有者を変更してよいのか
- 「BTC保有者へ1対1でECXを割り当てる」という説明と整合するのか
- 将来、別の休眠コインにも同様の例外を適用できてしまわないか

この仕様は、Drivechainの動作に不可欠なものではありません。Drivechainの技術評価と、ECX固有のコイン配分・所有権ポリシーは分けて考える必要があります。

また、正式なMainnet開始前に対象や実装が変更される可能性があります。記事公開後も最新のソースコードと公式仕様を確認すべき項目です。

## まとめ

eCash（ECX）は、Bitcoinネットワーク全体をDrivechainへ移行させるアップグレードではありません。

Bitcoinで採用されなかったBIP 300とBIP 301を実験するため、Bitcoinの履歴とUTXOセットを引き継いだ新しいチェーンを立ち上げるハードフォークです。

BIP 300はマイナー投票を使ったサイドチェーン資金の出入口を、BIP 301はマイナーがサイドチェーンを直接運用せずに関与するBlind Merged Miningを定義します。これにより、基軸チェーンを変更せず、用途ごとに異なるサイドチェーンを接続することを目指しています。

一方で、ECXはBTCとは異なる資産です。ハッシュレート、流動性、利用者、ウォレット、取引所対応などを独自に獲得しなければなりません。リプレイリスクやSatoshi時代のコイン再割り当てといった、ECX固有の技術・ガバナンス上の論点もあります。

今回のハードフォークで本当に問われるのは、ECXの価格だけではありません。長年議論されてきたDrivechainが、独立チェーン上で実際に利用され、安全に運用できるかどうかです。
