*Bitcoinは公開と順序付け、indexerはShielded Bitcoinのルールの検証を担当します。図の矢印はデータの流れで、indexerが資金を預かる意味ではありません。*

Bitcoinの取引は公開されています。アドレスに氏名が書かれていなくても、金額や入出力のつながりは見えます。では、送金の中身を隠しながら、勝手に残高を増やしていないことだけを確かめられるでしょうか。

**Shielded Bitcoinは、Bitcoinへ暗号化された送金データを公開し、外部のソフトウェアで正しさを検証するメタプロトコルの提案です。** Bitcoinのコンセンサスルールを変えずに、その上で別のルールを解釈する仕組みを目指します。

この記事では、2026年9月24日付の論文をもとに、送金の流れと残る課題を説明します。読了目安は約7〜9分。対象は内部送金の設計で、**普通のBTCを入出金する仕組みまで完成したと説明するものではありません。** [論文 §1.2][paper]

## Bitcoinが検証するものを増やさない

最初に、2つの検証を分けます。

Bitcoinノードは、通常どおりBitcoinトランザクションの署名や支出条件を検証します。しかし、そこに載せたShielded Bitcoinのデータを解釈して、内部残高の移転が正しいかまで判断するわけではありません。

その仕事をするのが**indexer**です。Bitcoinの履歴を読み、Shielded Bitcoinのルールで有効な送金だけを取り込みます。同じ仕様・初期状態・Bitcoin履歴を使う正しい実装同士は、同じ結果へ到達する設計です。[論文 §3・§4][paper]

| 層 | 確認すること |
| --- | --- |
| Bitcoin | Bitcoin取引が有効か、どの順序でブロックに入ったか |
| Shielded Bitcoinのindexer | 証明が正しいか、内部の価値を二重に使っていないか |
| ウォレット | 自分宛てのデータを復号できるか、何を保有しているか |

たとえるなら、Bitcoinは全員が参照できる掲示板で、indexerは掲示内容を決まったルールで読むソフトウェアです。掲示板に載ったからといって、その内容がShielded Bitcoinでも有効とは限りません。

## 残高を表す「note」

内部の価値は**note**という単位で扱います。未使用の価値を持ち主が後で使う、という点はUTXOに似ています。ただし、通常のUTXOそのものを暗号化するわけではありません。別のプロトコルで扱う記録です。

noteの中身には金額や受取側に関わる情報があり、公開時には暗号化します。使うときは古いnoteを消費し、新しいnoteを作ります。[論文 §5][paper]

説明用に、Aliceが10,000 sat相当のnoteを持ち、Bobへ3,000 sat相当を送るとします。内部で行いたいのは、次の更新です。

```text
消費：Aliceのnote  10,000 sat
作成：Bobのnote     3,000 sat
      Aliceの釣銭   7,000 sat
```

この数字は仕組みを説明するために書いています。設計上、観測者へこのまま公開されるものではありません。また、これは内部の価値保存だけを示す例で、データ公開に必要なBitcoinのマイニング手数料は別に考えます。

ここで疑問が生まれます。金額を隠したら、Aliceが3,000と7,000の代わりに、30,000と70,000のnoteを作っても分からないのではないでしょうか。

## 暗号化とゼロ知識証明は、役割が違う

暗号化は、noteの内容を受取人以外に読ませないために使います。**暗号化するだけでは、価値を不正に増やしていないことは証明できません。**

そこで送信者は、ゼロ知識証明を付けます。詳細な計算を省略すると、主に次の条件を、中身を公開せずに証明する役割です。

- 消費するnoteは、プロトコルの有効な記録の中に存在する。
- 送信者は、そのnoteを使う権限を持つ。
- 入力と出力の金額が釣り合い、不正な増額がない。

先ほどの例なら、観測者は「10,000」「3,000」「7,000」を読む代わりに、条件を満たす更新だという証明を検証します。[論文 §14][paper]

ただし、正しく作った送金を二度投稿した場合は、別の問題です。証明が正しいことだけでは、「もう使った」という履歴まで片付きません。

## nullifierで二重使用を防ぐ

noteを使う際には、**nullifier**という公開の使用済みマーカーを出します。同じnoteの二重使用は同じマーカーとして検出できる一方、マーカーからどの過去のnoteを消費したかを直接特定させない構成です。証明は、このマーカーが正しく導出されていることにも結び付きます。

indexerは、受理したnullifierの集合を保存します。新しい送金に既出のnullifierがあれば、二重使用として受け入れません。[論文 §9・§15][paper]

「誰の、いくらのnoteだったか」と、「同じ価値を二度使っていないか」を分けて扱うのが要点です。内容を隠すために、使用済みかどうかまで秘密にしてしまうわけではありません。

## 送信から受取までをつなげる

AliceからBobへの送金は、概念的には次の順序になります。

1. Aliceのウォレットが使うnoteを選び、Bob宛てと釣銭用のnoteを用意する。
2. 新しいnoteを暗号化し、nullifierとゼロ知識証明を組み合わせる。
3. それらのデータをBitcoinトランザクションで公開する。
4. indexerがブロックの履歴に沿って検証し、有効なら状態を更新する。
5. Bobのウォレットが自分宛てのnoteを見つけ、復号・確認する。

この説明では、細かなエンコードや暗号パラメーターを省略しています。論文の実装プロファイルでは、データの掲載方法としてOP_RETURNを指定していますが、実装間で一致させる必要のある選択や課題も残しています。[論文 §10・§11・付録A][paper]

indexerは秘密鍵を預かる必要がありません。ただし、利用しているindexerがデータを隠したり古い状態を返したりすれば、ウォレットは困ります。自分で検証できる設計と、スマートフォンが少ない通信量で安全に使えることは別の課題です。

## 隠せる情報と、残る手掛かり

この設計が狙うのは、内部送金の金額や相手、消費したnoteと過去のnoteの対応を直接公開しないことです。取引の存在まで消えるわけではありません。

| 隠す対象 | 公開されたままの情報・手掛かり |
| --- | --- |
| note内の金額や受取先 | 公開のタイミング、データ量 |
| どの過去のnoteを使ったか | 消費・作成するnoteの個数 |
| 内部送金の当事者の対応 | データ掲載用のBitcoin取引、手数料、その資金源 |

たとえば毎回、本人と結び付いた通常のBitcoinウォレットから掲載手数料を払えば、誰が投稿したかの手掛かりになります。特徴的な時刻や送金の形を繰り返すことも、候補を絞る材料です。[論文 §20・§22.3][paper]

したがって、「ゼロ知識証明があるから完全匿名」とは言えません。暗号が何を隠すかと、周辺の行動から何を推測できるかを分ける必要があります。

## 普通のBTCとの出入口が、もう一つの核心

ここまでの話は、内部でnoteを移す仕組みです。これをBTCとして使うには、普通のBTCを内部のnoteへ対応付ける**peg-in**と、noteから普通のBTCへ戻る**peg-out**が必要になります。

今回の論文は、この出入口を対象外と明記しています。提案者はPIPEs v2と呼ばれる研究を使う方向を示していますが、内部送金の証明だけで、出金まで安全だと結論することはできません。[論文 §1.2・§22][paper]

説明上の問いはシンプルです。「私が3,000 satのnoteを持つこと」と、「Bitcoin上の3,000 satを私が取り出せること」を、何が結び付けるのでしょうか。前者のルールだけ完成しても、後者の保証が自動で生まれるわけではありません。

この記事で確認した資料の範囲では、入出金の仕組み、安全性、可用性を別途評価する必要があります。通常のBTCをすぐに匿名化できる完成済みサービスとして扱わない理由は、ここにあります。

## ほかに残っている課題

証明方式にも前提があります。参照プロファイルが採るGroth16にはtrusted setupが必要で、正しい初期設定が安全性の条件になります。証明が短いという利点だけでなく、その生成・検証に使うパラメーターをどう準備するかも重要です。[論文 付録A.1][paper]

また、暗号化されたデータと証明をBitcoinに掲載する以上、ブロックスペースと手数料を使います。noteの個数、証明方式、掲載方法によって費用は変わり、プライバシーのための処理が無料になるわけではありません。

復元についても、秘密情報と公開履歴から状態を再構築する設計ですが、同期量や初期状態の扱い、入出金用データまで含めた運用は別途検討が必要です。公開履歴があることだけから、「端末を失ってもシードだけで即座に全部戻る」とまでは言えません。[論文 §16・§22][paper]

Shielded Bitcoinの読みどころは、**公開すること、内容を読めること、正しさを検証できることを切り分ける設計**にあります。Bitcoinのルールを変えない代わりに、別の検証ソフトウェアと暗号方式、そしてBTCとの出入口を組み合わせる必要があります。
