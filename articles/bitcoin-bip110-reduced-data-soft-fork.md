## はじめに

Bitcoinのブロックチェーンには、支払いに必要な情報だけでなく、画像や文書などの任意データを埋め込むこともできます。

こうした利用を「手数料を払った正当なブロックスペースの利用」と見るか、「すべてのフルノードへ保存コストを負わせるspam」と見るかは、Bitcoinコミュニティで長く議論されてきました。

この対立が2025年のBitcoin Core 30.0における`OP_RETURN`ポリシー変更をきっかけに再燃し、任意データをコンセンサスルールで制限する**BIP 110: Reduced Data Temporary Softfork**が提案されました。

BIP 110は一時的なソフトフォークとして設計されましたが、十分なマイナー支持を得ないまま強制シグナリング期間へ入り、2026年8月に少数派チェーンを発生させました。少数派チェーンの採掘はほぼ停止し、BIP 110は`Closed`になっています。

この記事では、BIP 110が何を制限しようとしたのか、Bitcoin Core 30.0との関係、ソフトフォークなのになぜチェーンが分裂したのかを整理します。

## 先に結論

BIP 110の要点は次のとおりです。

- Bitcoinへの任意データ埋め込みを減らすための、一年間限定のソフトフォークでした
- `OP_RETURN`を83バイトに制限するだけでなく、Taprootやwitnessを含む7つのコンセンサスルールを追加しました
- 有効化前に作られたUTXOは新ルールの対象外にするgrandfatheringがありました
- マイナーの55%がシグナルすればロックインする設計でした
- 支持が不足しても特定のブロック高から全ブロックにシグナルを要求する、強制シグナリングが組み込まれていました
- 実際のシグナリングはごく少数にとどまり、強制シグナリングを始めたBIP 110ノードがBTC本流から分離しました
- 少数派チェーンは十分なブロックを生成できず、BIP 110は2026年8月9日に`Closed`へ変更されました
- これは「Bitcoin全体がBIP 110を有効化した」事例ではなく、「少数派だけでソフトフォークを強制すると何が起きるか」を示す事例です

BIP 110の重要性は、任意データを減らすルールそのものだけではありません。mempool policyとconsensusの違い、ユーザー主導ソフトフォークの成立条件、ノード数とハッシュレートの関係を考える具体例になっています。

## 背景：Bitcoinへ任意データを埋め込む

Bitcoinのトランザクションは、本来、コインの所有条件を記述するためのデータです。しかし、トランザクションの一部を使って支払い以外のデータを記録できます。

代表的な方法には次のものがあります。

- `OP_RETURN` outputへデータを入れる
- 支払いに見えるoutput scriptへデータを埋め込む
- witnessへデータを入れる
- Taprootのscript pathへデータを入れる
- Ordinalsのinscription envelopeを利用する

`OP_RETURN` outputはprovably unspendableなので、UTXOセットへ残りません。しかしブロックの履歴には残るため、フルノードはブロックを検証・保存・配信する際にそのデータを扱います。

一方、データを公開鍵や支払い条件のように見せて埋め込むと、ノードが単純に「任意データだけを削除する」ことは困難です。Bitcoinにとって意味のあるスクリプトと、データ保存のためだけに作られたスクリプトを、プロトコルが意図によって判別できないためです。

## policyとconsensusの違い

BIP 110を理解するには、**policy**と**consensus rule**を区別する必要があります。

### policy

policyは、各ノードが未承認トランザクションをmempoolへ受け入れるか、ほかのノードへ中継するかを決めるローカルルールです。

```text
トランザクションを受信
  ↓
自分のpolicyを満たすか
  ├─ 満たす   → mempoolへ入れて中継
  └─ 満たさない → 中継しない
```

policyに違反するトランザクションでも、コンセンサス上有効なら、マイナーがブロックへ入れた後は有効なトランザクションとして受け入れます。

ノード運用者はpolicyを変更できます。また、通常のP2Pリレーを通らず、マイナーへ直接トランザクションを渡すこともできます。

### consensus rule

consensus ruleは、ブロックやトランザクションがBitcoinの履歴として有効かを決めます。

```text
新しいブロックを受信
  ↓
consensus ruleを満たすか
  ├─ 満たす   → 有効なブロック候補
  └─ 満たさない → ブロックごと拒否
```

ノード間でconsensus ruleが食い違うと、同じブロックを一方は有効、他方は無効と判断します。その状態が続けばチェーン分裂につながります。

BIP 110の大きな特徴は、従来policyで扱われることが多かった任意データ制限を、consensusへ移そうとしたことです。

## Bitcoin Core 30.0の`OP_RETURN`変更

Bitcoin Core 30.0では、デフォルトの`-datacarriersize`が100,000バイトへ引き上げられました。実際には最大トランザクションサイズへ先に到達するため、`OP_RETURN`サイズのpolicy上の上限は事実上撤廃されました。

さらに、一つのトランザクションへ複数のdata carrier outputを含めることも、デフォルトpolicyで許可されました。

ただし、これはconsensus ruleの変更ではありません。

```text
Bitcoin Core 30.0より前
  デフォルトpolicyでOP_RETURNを強く制限

Bitcoin Core 30.0
  デフォルトpolicyの制限を緩和

どちらのノードも
  consensus上有効なブロックの判定ルールは同じ
```

Core 30.0以前でも、83バイトを超える`OP_RETURN`を含むトランザクションがconsensus上無効だったわけではありません。独自policyを使うノードやマイナーは、それらを中継・採掘できました。

変更を支持する側は、任意データを完全に防げないなら、UTXOセットへ残り得る偽装outputではなく、明確に破棄可能な`OP_RETURN`へ誘導する方がよいと考えました。

反対する側は、デフォルト上限の撤廃がBitcoinを任意データ保存へ開放し、ノード運用者へ保存・配信コストや法的リスクを負わせると主張しました。

この対立から生まれた提案の一つがBIP 110です。

## BIP 110が追加しようとした7つのルール

BIP 110の正式名称は**Reduced Data Temporary Softfork**です。一年間の有効期間中、次の7つの制限をconsensus ruleとして追加する設計でした。

| No. | 制限 | 主な対象 |
| --- | --- | --- |
| 1 | 新しい`scriptPubKey`を34バイト以下に制限する。`OP_RETURN`は83バイトまで | 大きなoutput script、`OP_RETURN` |
| 2 | `OP_PUSHDATA*`のpayloadとscript argument witness itemを256バイト以下に制限する | 大きなdata push、witnessデータ |
| 3 | 未定義のwitness versionまたはTapleaf versionを使用するspendを無効にする | 将来のアップグレード領域 |
| 4 | Taproot annexを含むwitness stackを無効にする | Taproot annex |
| 5 | Taproot control blockを257バイト以下に制限する | 深いTaptree |
| 6 | `OP_SUCCESS*`を含むTapscriptを無効にする | 将来のopcode追加領域 |
| 7 | Tapscriptで`OP_IF`または`OP_NOTIF`を実行するspendを無効にする | inscription envelopeなど |

単純な`OP_RETURN`制限だけではありません。Taprootで将来のアップグレードに予約されている仕組みや、正当なスクリプト構成にも影響し得る広い変更でした。

### inscription envelopeとの関係

代表的なinscription envelopeは、概念的には次のような構造を使います。

```text
OP_FALSE
OP_IF
  任意データ
OP_ENDIF
```

条件がfalseなので、データ部分は実行されません。しかしデータ自体はwitness内に含まれ、ブロックへ記録されます。

BIP 110はTapscriptにおける`OP_IF`と`OP_NOTIF`の実行を禁止し、この形式を使いにくくしようとしました。

ただし、BIP 110自身も任意データやspamを完全には排除できないと認めています。データを細かく分割する、金融データのように見せる、別のスクリプト構造を使うといった回避が考えられるためです。

## なぜソフトフォークなのか

BIP 110は、従来有効だった一部のブロックを無効にする変更です。

```text
旧ノード
  従来ルールを満たすブロックを有効と判断

BIP 110ノード
  従来ルール
  ＋ BIP 110の追加制限
  を両方満たすブロックだけを有効と判断
```

BIP 110ルールを満たすブロックは、旧ノードから見ても有効です。新ノードが受け入れる有効ブロックの集合を狭くするため、分類上はソフトフォークです。

しかし「後方互換なソフトフォークなら分裂しない」という意味ではありません。新ルールを守るマイナーが少数しかいない状態で新ノードだけがルールを強制すると、旧ルール側の多数派ブロックを拒否し、少数派チェーンへ分かれます。

## UTXO grandfathering

BIP 110には、有効化前から存在するUTXOを追加制限の対象外にするgrandfatheringがありました。

```text
有効化前に作られたUTXO
  → 従来ルールでspend可能

有効化後に作られたUTXO
  → BIP 110の追加ルールも適用
```

既存のTaproot UTXOや事前署名トランザクションが突然使用不能になるリスクを抑えるためです。また、一年間の有効期間が終了すると、新しいUTXOを含めて追加制限を解除する設計でした。

それでも影響を完全には排除できません。

例えば、有効化後に承認される事前署名トランザクションが深いTaptreeや`OP_IF`を含み、そのoutputを制限期間中に特定のscript pathで使用する必要がある場合、想定したspendが無効になる可能性があります。

BIP 110は通常の支払いを守ることを目指していましたが、任意データと高度な金融プロトコルをルールだけで完全に区別するのは困難です。

## 一年間限定にした理由

BIP 110の追加制限は、52,416ブロック、およそ一年間だけ有効になる設計でした。

一時的にした理由の一つは、制限が将来のBitcoinアップグレードを妨げるためです。

- 未定義witness versionは、将来の新しいwitness programに使います
- `OP_SUCCESS*`は、Tapscriptへ新しいopcodeを追加するための仕組みです
- Taproot annexも、将来の拡張領域として予約されています
- Taptreeの深さや`OP_IF`の制限は、高度なoff-chain protocolへ影響し得ます

BIP 110を恒久化すると、これらの領域を使う新機能をソフトフォークで導入しにくくなります。そのため、まず単純な制限を一年間導入し、その間に長期的な解決策を検討する考え方でした。

一方、批判する側からは、将来のアップグレード経路を制限する変更を短期間で導入すること自体が危険だと見られました。

## BIP 110の有効化方式

BIP 110は、修正版BIP 9によるシグナリングを採用していました。主なパラメータは次のとおりです。

| 項目 | 値 |
| --- | --- |
| deployment名 | `reduced_data` |
| version bit | bit 4 |
| threshold | 1,109 / 2,016ブロック、55% |
| 強制シグナリング期間 | ブロック961,632〜963,647 |
| 最終ロックイン高 | ブロック963,648 |
| 最大有効化高 | ブロック965,664 |
| 有効期間 | 52,416ブロック、約一年 |

通常のBIP 9では、十分な割合のマイナーが対応準備を示した場合にロックインします。

BIP 110はこれに加え、期限までに55%へ到達しなくても、ブロック961,632以降はシグナルしていないブロックをBIP 110ノードが拒否する**mandatory signaling**を組み込んでいました。

```text
自主シグナリング期間
  ↓
55%へ到達すればLOCKED_IN
  ↓ 到達しなくても
ブロック961,632からmandatory signaling
  ↓
非シグナルブロックを拒否
  ↓
ブロック963,648で遅くともLOCKED_IN
  ↓
ブロック965,664でACTIVE
```

設計上は、強制シグナリングによって最終的に55%へ到達し、追加ルールを有効化する想定でした。

しかし、十分なハッシュレートが強制ルールへ従わなければ、BIP 110ノードが拒否したブロックの上に多数派マイナーが採掘を続けます。この場合、BIP 110ノードだけが多数派チェーンから取り残されます。

## 2026年8月に何が起きたのか

自主シグナリング期間中、BIP 110は必要な55%のマイナー支持を得られませんでした。強制シグナリング開始直前でも、シグナリングするハッシュレートは数%未満と観測されていました。

2026年8月8日ごろ、ブロック961,632からBIP 110ノードが非シグナルブロックを拒否し始めました。しかし大部分のマイナーは従来のBitcoinチェーン上で採掘を続けました。

```text
                             ┌─ BTC本流
ブロック961,631 ─ 分岐地点 ─┤  大部分のハッシュレート
                             │  非シグナルブロックも有効
                             │
                             └─ BIP 110少数派チェーン
                                非シグナルブロックを拒否
                                ごく少数のハッシュレート
```

少数派チェーンではブロック生成が極端に遅くなりました。2026年8月18日のBitcoin Optechの振り返りでは、BTC本流が1,000ブロック以上先へ進んだ時点でも、BIP 110側は5ブロック程度しか生成できていないと説明されています。

BIP 110の変更履歴では、チェーン分裂と採掘停止を受け、2026年8月9日にステータスを`Closed`へ変更したと記録されています。

つまり、BIP 110の任意データ制限がBitcoin上でACTIVEになったわけではありません。ルールを強制した少数派がBitcoinの最多workチェーンから分離し、その少数派チェーンも実用的に進まなくなりました。

## なぜ少数派チェーンは進めなかったのか

Bitcoinの採掘難易度は、直近2,016ブロックの生成状況をもとに調整されます。

BIP 110側はBitcoin本流から分かれても、分岐直前の高い採掘難易度を引き継ぎました。ところが、実際にBIP 110側で採掘するハッシュレートはごくわずかでした。

```text
Bitcoin本流
  高いdifficulty
  ＋ 大きなhashrate
  → 約10分間隔で進む

BIP 110側
  同じ高いdifficulty
  ＋ ごく小さなhashrate
  → ブロックをほとんど発見できない
```

難易度が下がるには次の2,016ブロックへ到達する必要があります。しかしブロック自体をほとんど生成できないため、難易度調整まで進めません。

これは、Bitcoinから少数のSHA-256dハッシュレートだけで分岐するときに起きる典型的な問題です。

## ソフトフォークなのになぜチェーン分裂したのか

ソフトフォークの後方互換性が意味するのは、新ルールに従ったブロックを旧ノードも有効と判断できることです。新ルールを無視した多数派チェーンを、新ノードが必ず受け入れるという意味ではありません。

十分なハッシュレートがソフトフォークを強制する場合、旧ルールだけに従うブロックが一時的に作られても、新ルール側のチェーンが累積workで追い越し、ネットワークは一つへ収束できます。

```text
新ルール側がハッシュレート多数
  → 新ルール準拠チェーンが最多workになる
  → 旧ノードも同じチェーンを追う
```

反対に、新ルールを強制するハッシュレートがごく少数の場合、旧ルール側が最多workを積み上げます。

```text
新ルール側がハッシュレート少数
  → 旧ルール側が最多workになる
  → 新ノードはそのチェーンをルール違反として拒否
  → 少数派チェーンへ分裂
```

BIP 110では後者が起きました。

フルノードの台数やSNS上の支持だけでは、少数派チェーンのブロックを生成できません。新ルールを強制しながらチェーンを実用的に進めるには、そのルールに従う採掘能力が必要です。

## Lightning Networkへの影響

チェーンが分裂すると、同じ秘密鍵が両方のチェーン上のUTXOを制御します。BIP 110には、Bitcoin Cashで導入されたような双方向の強制的リプレイプロテクションはありませんでした。

BIP 110準拠のトランザクションは、通常のBitcoinルールも満たすため、BTC本流へリプレイされる可能性があります。反対方向では、BTC本流で有効なトランザクションがBIP 110の追加制限に違反し、少数派側では無効になる場合があります。

Lightningチャネルでは、両チェーン上に同じfunding outputと事前署名済みのcommitment transactionが存在します。そのため、ノードがどちらのチェーンを信頼するかによって、チャネルの状態やforce closeの結果が異なる可能性があります。

特に問題になるのは次のような状況です。

- Lightningノードのchain backendがBIP 110少数派チェーンを追う
- 相手はBTC本流を追う
- 一方のチェーンだけでcommitment transactionが承認される
- HTLCのtimeoutやCSV delayが、異なる速度で進む二つのチェーン上で別々に経過する
- 一方で公開されたトランザクションや署名が、もう一方でも利用される

BIP 110側はブロック生成が極端に遅くなったため、ブロック高を基準にするLightningのタイムロックも想定どおり進みません。

チェーン分裂時にLightningを安全に維持するには、単に「自分のノードが新ルールを支持する」だけでなく、ウォレット、相手ノード、watchtower、取引所、マイナーなどがどのチェーンを追うかを考える必要があります。

## BIP 110を支持する主張

BIP 110の提案文では、主に次の理由が挙げられています。

### Bitcoinを通貨として優先する

ブロックスペースを任意データが消費すると、支払いの手数料が上がり、Bitcoinを決済に利用しにくくなるという考えです。

### ノード運用者が継続的なコストを負う

データをブロックへ入れる利用者はマイナーへ一度だけ手数料を払います。一方、その後データを保存・配信するフルノード運用者は、その手数料を受け取らず継続的なコストを負います。

### policyだけではマイナーを拘束できない

多くのノードがトランザクションをリレーしなくても、マイナーが直接受け取りブロックへ入れれば、ノードはconsensus上有効なブロックとして受け入れます。確実に制限するにはconsensus ruleが必要だという主張です。

### UTXOセットの肥大化を抑える

データがspendableに見えるoutputへ埋め込まれると、UTXOとして保存される可能性があります。BIP 110は通常の`scriptPubKey`を34バイト以下に制限し、UTXOセットへの負担も抑えようとしました。

## BIP 110に対する批判

一方、BIP 110には次のような批判がありました。

### 任意データを完全には防げない

特定のデータ形式を禁止しても、別のスクリプトや小さなpushへ分割できます。利用者がデータを支払い情報に見せかければ、意図をconsensus ruleで判定できません。

### データを`OP_RETURN`から別の場所へ追い出す可能性

`OP_RETURN`は明確にunspendableなので、UTXOセットから削除できます。そこを厳しく制限すると、データが公開鍵や通常outputに見える形式へ移り、かえってノードの負担が増える可能性があります。

### policy変更をconsensus変更で打ち消すのは範囲が大きい

Bitcoin Core 30.0の変更はデフォルトのリレー・マイニングpolicyでした。各ノードは83バイトへ戻せます。それに対してBIP 110は、違反トランザクションを含むブロック全体を無効にする変更です。

### 将来のアップグレード経路を制限する

未定義witness version、Taproot annex、`OP_SUCCESS*`は将来の拡張のために予約されています。一時的であっても、これらを使用不能にすることで新しいプロトコルや実験へ影響します。

### 有効化方式が支持規模に対して攻撃的だった

55%という低めのthresholdに加え、支持が不足しても非シグナルブロックを拒否するmandatory signalingを採用しました。実際のマイナー支持が数%未満の状態では、Bitcoin全体を収束させるより少数派を分離させる結果になりました。

## BIP 110とBLAKE2bハードフォーク

BIP 110の少数派チェーンは、高いdifficultyと低いhashrateの組み合わせによって進めなくなりました。

その後、一部の支持者はProof of WorkをBitcoinのSHA-256dからBLAKE2bへ変更し、difficulty問題を切り離した新しいチェーンを開始しました。プロジェクト側の説明では、最初のBLAKE2bブロックは961,640で、2026年8月30日に生成されたとされています。

ここでは二つを分ける必要があります。

```text
BIP 110
  従来より厳しいルールを加えるソフトフォーク案
  SHA-256dの少数派チェーンを発生させた
  その後Closed

BLAKE2bチェーン
  Proof of Workを変更するハードフォーク
  BIP 110失敗後に別チェーンとして開始
```

PoWの変更は、旧ノードが新しいブロックを有効と判断できない非互換変更です。そのため、こちらは明確なハードフォークです。

BLAKE2bチェーンの存在を「BitcoinでBIP 110が有効化された」と説明するのは正確ではありません。BTC本流とは別のネットワークです。

## BIP 110とeCash（ECX）の違い

2026年8月には、Drivechainを実装するeCash（ECX）のハードフォーク計画も進んでいました。どちらもBitcoinの履歴から分岐するため混同されやすいですが、目的も経緯も異なります。

eCashの仕組みについては、[Bitcoinから分岐するeCash（ECX）とは何か](/articles/bitcoin-ecash-drivechain-hard-fork)で詳しく説明しています。

|  | BIP 110少数派／BLAKE2b | eCash（ECX） |
| --- | --- | --- |
| 主な目的 | 任意データの制限 | Drivechainの実装 |
| 出発点 | BTC上でのソフトフォーク強制 | 最初から独立チェーンを作る計画 |
| 主な提案 | BIP 110 | BIP 300、BIP 301 |
| 分裂の経緯 | 支持不足のmandatory signaling | 計画されたハードフォーク |
| PoW | 当初SHA-256d、後に一部がBLAKE2bへ変更 | SHA-256dを予定 |
| BTC本流への影響 | BTC側は従来ルールで継続 | BTC側は従来ルールで継続 |

BIP 110は「Bitcoin上で新ルールを強制しようとして少数派になった事例」です。ECXは「Bitcoinで採用されていない機能を、別チェーンで稼働させるための計画」です。

## よくある誤解

### BitcoinでBIP 110が有効化された

有効化されていません。強制シグナリングを実行したノードが少数派チェーンへ分かれ、採掘が停滞しました。BIPのステータスも`Closed`です。

### BIP 110は`OP_RETURN`だけを83バイトへ戻す提案だった

それだけではありません。witness item、未定義witness version、Taproot annex、control block、`OP_SUCCESS*`、`OP_IF`なども制限する7つのルールでした。

### Bitcoin Core 30.0がブロックサイズを拡大した

拡大していません。Core 30.0は`OP_RETURN`に関するデフォルトpolicyを変更しましたが、ブロックweightやconsensus ruleは変更していません。

### ソフトフォークならチェーン分裂しない

新ルールを強制する側が十分なハッシュレートを持たなければ、旧ルール側の最多workチェーンを拒否し、少数派チェーンへ分かれます。

### フルノードの多数決で有効化できる

フルノードは自分が受け入れるブロックを選べますが、ブロックを生成するのはマイナーです。新ルール側の採掘能力が不足すると、チェーンを実用的な速度で進められません。

## BIP 110から分かること

BIP 110は任意データ論争への提案でしたが、その結果はBitcoinのアップグレード方法について多くの論点を示しました。

### policyとconsensusは影響の大きさが違う

policyはノードごとに選択でき、違反トランザクションがブロックへ入れば受け入れます。consensus ruleはブロック自体を拒否するため、意見の不一致がチェーン分裂になります。

### economic majorityとhashrateの支持が必要になる

ユーザー主導ソフトフォークでも、取引所、ウォレット、事業者、マイナーなどがどのチェーンをBitcoinとして扱うかが結果を左右します。ノードソフトウェアを公開するだけでは、ネットワーク全体の合意にはなりません。

### 一時的なルールでも導入リスクは一時的ではない

BIP 110のデータ制限は一年で終了する設計でした。しかし、有効化時に生じるチェーン分裂、リプレイ、Lightningチャネルへの影響は、有効期間が限定されていても発生します。

### Bitcoinの用途を誰が決めるかという問題が残る

任意データを正当な利用と見るかspamと見るかは、単純な技術問題ではありません。マイナーが手数料を得る権利、ノード運用者が保存を拒む権利、利用者が任意のトランザクションを作る自由が衝突します。

BIP 110は閉じられましたが、「Bitcoinは何のためのネットワークか」「制限をpolicyとconsensusのどちらで実施すべきか」という議論は終わっていません。

## まとめ

BIP 110は、Bitcoin上の任意データを減らすため、7つの制限を一年間だけコンセンサスルールへ追加するソフトフォーク案でした。

提案の背景には、Bitcoin Core 30.0による`OP_RETURN`のデフォルトpolicy変更と、Bitcoinを決済ネットワークとして優先すべきだという考えがありました。

しかしBIP 110は、十分なマイナー支持を得ないままmandatory signalingを開始しました。大部分のハッシュレートは従来チェーン上で採掘を続け、BIP 110を強制するノードは少数派チェーンへ分離しました。そのチェーンは分岐前の高いdifficultyを引き継いだため、ほとんどブロックを生成できず、BIP 110は`Closed`になりました。

BIP 110はBitcoinで有効化されたソフトフォークではありません。少数派によるルール強制が、ハッシュレートと経済的支持を得られなかった事例です。

そしてこの事例は、ソフトフォークであっても合意形成に失敗すればチェーン分裂が起こること、policyとconsensusの間には大きな隔たりがあることを示しています。
